# 关键链项目管理小平台（CCPM Platform）

后端用 FastAPI（Python 3.12）做全部计算，数据落在挂载卷上的一个 SQLite 库；
前端 React 18 + Vite 只做录入与展示。运行镜像由两阶段构建：
`node:20-alpine` 打前端静态文件 → 拷进 `python:3.12-slim`，由后端同时提供页面和接口。

- 计划阶段：任务网络 + 多资源容量 → 资源受限排程 → 关键链 → 项目缓冲 / 汇入缓冲 → 甘特图
- 执行阶段：追加式汇报流 → 状态投影 → 关键链完成% / 项目缓冲消耗% → 发烧图（绿/黄/红）
- 汇报乱序到达自动插回重算；重复编号幂等；历史时刻可回放；重启从汇报流恢复；并发收敛到串行结果
- 多项目组合：共享资源池 + 鼓资源 → 各项目按鼓的节拍错开排入（起步偏移），组合时间轴 + 鼓负荷曲线；排入并发等价于串行、重启后偏移不变

## 2. 数据模型

- **资源**：名字 + 可用数量（非负数）。可声明 `shared: true` 表示该资源取自组合的
  共享资源池（见 §8）；不声明即为项目私有的一份。
- **任务**：名字、紧前任务列表、资源占用（资源名 → 数量，可多种）、
  **激进工期** `aggressive`（50% 概率口径的乐观工期）、
  **保守工期** `conservative`（安全工期），单位均为工作日。
- **项目**：名字、资源列表、任务列表、发烧图黄线/红线（0–100，黄≤红，默认 50/80）。
- **组合（portfolio）**：名字 + **共享资源池**（资源名 → 池容量）+ 可选的指定鼓资源；
  成员项目按加入顺序各持有一个组合时间轴上的**起步偏移**。

计划阶段一律按**激进工期**排程，保守与激进之差只用于推算缓冲。

## 3. 排程规则（资源冲突消解）——确定性串行 SGS

资源受限关键链识别是 NP 难问题（等价于 RCPSP），本平台采用一个**确定性的
串行进度生成方案（serial SGS）+ 固定优先级**，而不是求全局最优：

1. **就绪选择**：维护“所有紧前任务都已排定”的就绪集合。按
   `（最长激进尾长 tail 降序，任务名升序）` 选下一个。
   `tail(t) = aggressive(t) + max(tail(后继))`，即“这个任务身后还压着多长的依赖链”。
   这是 LPT（长任务优先）类规则：下游链长、自身长的任务先占资源。
2. **最早可行时刻**：起点不早于所有紧前任务完成时刻；逐单位工作日检查任务执行窗口内
   每种所需资源的空闲容量。容量按连续时间段剖面维护，因此“中途被释放出来的容量窗口”
   也会被正确利用。
3. **阻塞推延**：若某时刻容量不足，把任务推到**最早结束的阻塞任务的完成时刻**，
   重新检查；重复直到可行。最后一次把它放行的那些占用任务（瓶颈资源的释放者）记为该任务的
   **资源紧前任务**，构成一条额外的“资源边”。
4. 零工期任务不占资源、可与其紧前任务同一时刻完成。

> **关键链识别**：在“紧逻辑边（紧前任务完成时刻恰好等于任务开始时刻）+ 资源边”
> 组成的图上取最长路径。所有边都是紧的（无松弛），因此该最长路径长度恒等于排程 makespan，
> 一定是一条真正的关键链。

### 3.1 无冲突时必须退化为关键路径

没有资源冲突时，每个任务都排在“紧前任务最大完成时刻”，最长紧逻辑路径就是
纯依赖关键路径。测试 `test_no_resource_conflict_cc_equals_critical_path` 锁定该性质。

四任务算例（A4 / B6 / C3 / D2；A→B、C；B、C→D；B、C 共用 1 名工程师）：

| 情形 | 关键链 / 路径 | 长度 |
|---|---|---|
| 不看资源 | A→B→D（关键路径） | **12** |
| 计入资源（B 先占工程师，C 推到 B 后） | A→B→C→D（关键链，资源边 B→C） | **15** |

### 3.2 等长关键链如何确定地选一条

最长路径 DP 在长度相当时，先取**经过任务更多**的链（保证零工期的里程碑节点也挂在关键链上），
再比较路径上**任务名元组的字典序，取更小者**。任务选择的 `(tail, name)` 也是全序。
因此同一份输入无论提交多少次、并行还是串行，排程与关键链**逐字节一致**
（测试 `test_deterministic_same_input_same_output`）。

### 3.3 这套规则在什么网络上会偏长（已知偏差来源）

这是启发式而非最优算法，以下网络结构上可能得到比最优解偏长的 makespan：

- **短视的长任务优先**：tail 只看依赖链长度，不看全局资源占用。
  一个“身后链长但资源需求很窄”的任务先占资源，可能把一个“短但能 unlock 一串任务”的
  任务挡在后面，而换一个先占顺序本可在同工期内完成（典型 RCPSP 优先级规则次优场景）。
- **只推到最早阻塞任务结束**：任务被推时只前推到“当前最早放行点”，不会主动跳过
  一个近期可行但会与后续任务二次冲突的窗口（可能引发连续小推延、碎片化资源剖面）。
- **资源边只记录最后一次放行者**：多个资源联合造成的等待中，只释放非瓶颈资源的任务
  不会成为关键链边；这是有意的（避免假关键边），但在多重资源高度耦合的网络里，
  关键链可能只反映其中一个瓶颈而漏掉并列瓶颈。
- **容量按单位桶检查、时刻用数值而非日历**：计划阶段不考虑节假日（执行阶段的简化
  日历见 §6）。

`GET /api/rule` 返回规则文字，前端侧栏可查看。

## 4. 缓冲口径

采用经典 **50% 剪切粘贴（cut-and-paste）** 规则：

```
链缓冲 = 1/2 × Σ (conservative − aggressive)      （对链上每个任务）
```

依据：保守工期可看作“激进工期 + 任务自带的安全余量”，把各任务一半的安全余量
剪切下来汇聚成链尾的一个缓冲，既保留聚合后的风险保护，又消除各任务各自窝工
（学生综合症）带来的膨胀。

- **项目缓冲 PB**：放在关键链末端，`[makespan, makespan + PB]`。
- **汇入缓冲 FB**：每个“非关键链任务 → 关键链任务”的汇入弧放一个，
  大小按汇入该点的最长非 CC 依赖链上任务的 spread 和的一半计算；
  位置为 `[CC任务开始 − FB, CC任务开始]`，即贴着汇入点放置。
  汇入链只沿**逻辑依赖**回溯（不沿资源边），这是关键链方法的标准口径。
- 缓冲**不挪动已排任务**。若 FB 大于汇入点前的自由时差（缓冲左界越过了汇入链末端工作），
  该缓冲标记 `overflow=true`（甘特图红框虚线），提示计划者：这个汇入点本身已经贴近关键链，
  需要人工决定是否压缩/重排，而不是悄悄改计划。

缓冲放在 0.5 工作日粒度上（允许半天），因此：

### 同比缩放性质

所有工期同乘正整数 k 时，排程形状与关键链不变，任务时刻、makespan、缓冲**同比放大 k 倍**。
50% 因子是精确齐次的（不做取整），测试 `test_scaling_preserves_chain_and_scales_length_and_buffers`
对 k = 2,3,7,100 锁定该性质。

四任务算例：关键链 spread 和 = (8−4)+(12−6)+(6−3)+(4−2) = 15，PB = **7.5**，计划承诺工期 15 + 7.5 = 22.5。

## 5. 输入校验（拒收并指出具体字段）

以下输入返回 `422`，错误体为 `{"errors":[{"field": ..., "message": ...}]}`，
`field` 精确定位，例如 `tasks[2].predecessors[0]`、`tasks[0].resources.E`：

- 任务依赖成环（`tasks.predecessors`，message 给出环路径）；任务依赖自身
- 引用不存在的任务（`tasks[i].predecessors[j]`）
- 引用不存在的资源（`tasks[i].resources.<资源名>`）
- 激进工期 > 保守工期（`tasks[i].aggressive`）
- 工期或数量为负
- 某任务资源需求量 > 该资源总量
- 黄线/红线不在 0–100，或黄线高于红线
- 任务/资源重名、空名称、非数值等结构问题同样逐字段报错

## 6. 汇报流语义（执行阶段）

每条汇报：`report_id`、`task`、`timestamp`（ISO-8601，带 Z 或偏移量；无时区按 UTC）、
`remaining`（剩余工作日）或 `completed: true`。

| 议题 | 选定行为 |
|---|---|
| 存储方式 | **只追加**，历史永不改写；汇报存在独立 `reports` 表，`UNIQUE(project_id, report_id)` |
| 重复编号 | **幂等**：同一 `(项目, report_id)` 第二次提交直接返回已有状态 `duplicate:true`，不新增行、不改写 |
| 早于最近时刻的汇报 | **插入正确位置并重算**（不是拒收）。所有状态都由“按 `(timestamp, report_id)` 排序后的汇报流”重放得出，因此插入后全局只有一个一致状态 |
| 同时刻同任务 | 同一时刻对同一任务的多条汇报是**同一瞬间的多张快照**：状态投影只应用该时刻在编号序下的最后一条（不会把 0 工作日流逝记成虚假偏差）；每条汇报仍各有自己的轨迹点（点标签是该条汇报） |
| 同时刻不同任务 | 互不影响，按各自时刻参与重放 |
| 并发提交 | 写入用进程内锁串行化 + 库级唯一约束；最终状态等于按上述顺序逐条串行提交的结果（测试 `test_concurrent_reports_equal_serial_state`） |

**速度与偏差（slip）**：对同一任务的相邻两次汇报，假设其间任务连续工作，
经过 `elapsed` 个工作日（按简化工作日历），消耗了 `上次剩余 − 本次剩余` 个工作量。

```
slip += elapsed − consumed      # >0 落后，<0 提前，=0 按计划
```

- 首次汇报（任务开工）不产生 slip；
- 无过程汇报直接报完成：按准时完成（slip 0，速度取计划速度 1）；
- 完成后又出现更大的剩余值（返工/重估）：任务重新进入进行中，新工作量与经过时间计入 slip；
- **简化工作日历**：周一到周五为工作日，每个工作日按 24 小时计，周末不计，
  不考虑节假日（`app/calendar.py`）。

## 7. 关键链在执行期的策略：冻结

选定 **冻结计划时的关键链**，执行过程中**不随汇报重新识别**。发烧图的
x（完成%）与 y（缓冲消耗%）始终锚定冻结链上的任务集合。

理由与影响（对缓冲消耗曲线）：

- **冻结链**：曲线连续、可解释、可审计——今天的 60% 与上周的 60% 指向同一批任务；
  缓冲被什么任务吃掉一目了然。代价是：当实际执行使资源形态大变时，冻结链可能“过时”，
  真实新瓶颈不会自动成为监控对象，需要重新建项目/重排基线。
- （未采用的另一极：每次汇报都重排。它能反映现实，但关键链任务集合会跳变，
  完成度和缓冲分母随之改变，曲线会出现不连续跳点，历史点与新口径不可比。）

当前实现是纯冻结；若后续要切换，建议的切换条件是“重排后关键链任务集合变化且新 makespan
超出项目缓冲”，并保留旧链轨迹作为带版本号的历史曲线。

### 发烧图坐标与分区

- **x = 关键链完成百分比**：CC 任务已挣得工作量 / CC 激进总量。
  已完成按激进工期计；进行中按 `aggressive − remaining`（下限 0）计。
- **y = 项目缓冲消耗百分比**：`max(0, Σ CC 任务 slip) / PB × 100`，可能超过 100（缓冲耗尽）。
  项目缓冲为 0 时，任何正 slip 直接记 100%。
- **分区**：两条从原点出发的射线，经过 `(100, 黄线)` 与 `(100, 红线)`。
  点在黄线射线以下为绿，在红线射线以上为红，之间为黄；x=0 而 y>0 直接为红。
  线本身：压黄线判绿，压红线判红（含边界，确定性）。
- 汇入缓冲有同样口径的各自消耗视图（按直接汇入该点的非 CC 任务 slip 汇总），
  随点返回，主图只用项目缓冲。

### 历史回放

`GET /api/projects/{id}/state?at=<ISO时刻>` 只回放 `timestamp ≤ at` 的汇报，
与“把世界只运行到那一时刻”逐项相同（测试 `test_historical_replay_matches_prefix`）。
轨迹接口对每条汇报后的时刻都给一个点，前端点击点即可查看当时各任务剩余工期。

### 重启恢复

项目输入与计划 JSON、全部汇报都在 SQLite（WAL 模式，挂在 `/data` 卷）。
重启后状态完全由汇报流重放得出，不缓存任何派生状态，因此重启前后
当前状态与整条轨迹一致（测试 `test_restart_recovers_identical_state`）。

## 8. 多项目组合：共享资源池与鼓错峰

单项目视图看不到的争抢发生在项目之间。组合把多个项目放进同一个资源池上下文，
由后端按**鼓（drum）**的节拍把各项目错开排入，而不是让各项目各排各的、执行期再互相踩。

### 8.1 池中资源与项目的关系

- 组合拥有自己的**共享资源池**：资源名 → 池容量（非负数），可在组合视图里维护。
- 项目录入时可在资源上声明 `"shared": true`：该资源取自组合的池子，而不是自己私有的一份。
  声明后项目的**独立计划仍按其申报容量排程**（项目可以先建、后加入组合，也可以永不加入）。
- 项目加入组合时，**名字与池中资源相同的项目资源一律按池资源计**——无论是否显式声明。
  这是老项目（建组合之前录入、没有任何声明）加入组合的方式：在组合语境里，同名资源
  就是那一份共享资源，不存在"项目私有的同名一份"。
- 加入校验（`422`，与网络校验同样逐字段报全）：
  - `resources[i].name`：声明了 `shared` 的资源名不在池里；
  - `resources[i].capacity`：池资源的申报容量超过池容量（否则独立计划内部就可能
    并行占用超过池子总量的资源，任何偏移都无法满足鼓不变式）；
  - `tasks[j].resources.<资源名>`：单个任务对池资源的需求超过池子总量。
- 重复加入同一组合是幂等的：返回既有排布，不产生第二个成员记录。

### 8.2 鼓怎么定（本版的取舍）

鼓 = 组合里唯一用来错峰的池资源。两种来源，可兼得：

1. **管理员指定**：建组合或维护资源池时把 `drum` 设为某个池资源名（必须在池里，否则 422）。
2. **按负荷自动识别**（未指定时）：负荷 = `Σ(任务占用 × 激进工期) / 池容量`，
   即"该资源独自消化全部需求需要的时间"——经典瓶颈度量。负荷最高者为鼓；
   **并列时取资源名字典序最小者**（全序，确定性）。自动识别发生在**首次产生正负荷的
   排入**，结果**冻结**并持久化：此后新项目的负荷不再改变鼓。

为什么冻结而不是每次重识别：鼓一旦中途切换，早期项目是按旧鼓错开的，新鼓的占用
剖面可能已然超容，且没有任何后续偏移能修复——"鼓任何时刻不超池容量"这条不变式
就永久失效了。冻结后每次排入都约束同一只鼓，不变式对全部历史成立。

- 好处：零配置即可用；负荷度量直指瓶颈；冻结保证不变式与可审计性（每条偏移都能
  用"当时的鼓 + 当时的占用剖面"重放解释）。
- 短处：自动识别只反映首次排入时的需求形态，组合后续重心转移不会自动跟随；
  负荷用激进工期估计，不含执行期偏差。组合成熟后建议管理员显式钉住鼓
  （重新指定只影响之后的排入，已有偏移一律不重算）。

### 8.3 错峰排入规则

项目排入组合时，**它自己的关键链形状、链长和缓冲都不变**，只是整体在组合时间轴上
获得一个起步偏移 `offset ≥ 0`，使鼓在任何时刻的占用都不超过池子容量：

1. 已排项目的偏移与鼓占用**不再变动**；新项目在剩余容量里取**最早可行偏移**——
   这就是"新加入的项目排在已排项目之后"：容量允许时（池容量 > 单项目需求）新项目
   可以与已排项目并行，容量不足时自然排到已排项目让出的位置之后。
2. 推延规则与单项目排程同源：在最早超容时刻，把偏移推到"最早结束的阻塞占用"的
   释放点，重查直到可行。偏移严格递增且取值于有限候选集，因此确定、可终止。
3. **项目之间在鼓上不留容量缓冲**：新项目的鼓占用可以紧贴上一次释放的时刻开始
   （验收算例中第二份的工程师占用从组合第 13 个工作日开始，恰好接上第一份让出的位置）。
4. 池里**其它**共享资源本版不错峰：排布完成后若某非鼓池资源在某时段的总占用超过
   池容量，在组合视图里逐条列出（资源、时段、占用/容量）提示人工调整；鼓本身因
   池容量被改小而超历时也同样列出。

四任务算例（池里 1 名工程师，原样录两份依次加入）：第一份偏移 0、链长 15；
第二份偏移 9、组合第 24 个工作日完成，全程工程师占用 ≤ 1，两份关键链都是 A、B、C、D。
（测试 `test_acceptance_two_copies_staggered_on_one_engineer` 锁定。）

### 8.4 并发与持久化

- 排入 = "读成员与占用剖面 → 算偏移 → 写成员记录"，整段在存储层进程锁内完成
  （`store.transaction()`）。两个排入请求同时到达时串行化执行，结果等同于它们按
  某一先后顺序依次排入；鼓不会因并发被超额占用。同一组合状态下偏移计算是纯函数，
  同一份输入多次执行得到的偏移一致（测试 `test_concurrent_joins_equal_serial`、
  `test_same_input_same_offsets`）。
- 组合、资源池、鼓（指定与自动冻结）、成员、排入顺序（`join_seq`）与各项目偏移
  全部落在 SQLite（`portfolios` / `portfolio_members` 两表）。重启后组合成员、
  排入顺序和各项目偏移与重启前完全一致（测试 `test_restart_recovers_identical_portfolio_state`）。
- 老接口行为一律不变：项目的录入、计划、汇报、发烧图、历史回放都不感知组合
  （测试 `test_membership_does_not_change_project_endpoints`）。

## 9. HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查 |
| GET | `/api/rule` | 排程规则文字 |
| POST | `/api/projects` | 录入/导入任务网络，返回计划（422 逐字段错误） |
| GET | `/api/projects` | 项目列表 |
| GET | `/api/projects/{id}` | 项目输入 + 计划 + 阈值 |
| POST | `/api/projects/{id}/reports` | 追加汇报（幂等），返回最新状态点 |
| GET | `/api/projects/{id}/reports` | 汇报流（确定顺序） |
| GET | `/api/projects/{id}/state?at=` | 当前或历史时刻状态点 |
| GET | `/api/projects/{id}/trajectory` | 发烧图全部轨迹点 |
| POST | `/api/portfolios` | 建组合（名字 + 资源池 + 可选鼓；422 逐字段） |
| GET | `/api/portfolios` | 组合列表（含成员数、当前鼓） |
| GET | `/api/portfolios/{id}` | 组合视图：池、鼓、成员偏移、时间轴、鼓负荷曲线、冲突提示 |
| PUT | `/api/portfolios/{id}` | 维护名字 / 资源池 / 鼓（在用的池资源不可删；422 逐字段） |
| POST | `/api/portfolios/{id}/projects` | 把项目按鼓错峰排入（幂等；422 逐字段 / 409 池容量已被既有排布占满） |

## 10. 代码结构

后端核心逻辑按职责拆成独立模块，不挤在一个大文件里：

```
backend/
  app/
    models.py       # 输入/输出数据结构
    validation.py   # 网络建模与逐字段校验（环、悬空引用、工期、容量、阈值）
    scheduler.py    # 资源冲突消解（串行 SGS + 尾长优先级 + 阻塞推延）、纯依赖关键路径
    chain.py        # 关键链（紧逻辑边+资源边最长路径）、汇入链识别
    buffers.py      # 缓冲推算与放置（50% 规则、overflow 标记）
    planning.py     # 计划阶段编排 + 规则文字
    calendar.py     # 简化工作日历（周一~五）
    reports.py      # 汇报结构、载荷校验、确定排序
    state.py        # 汇报流 -> 各任务运行时状态（速度/slip）投影
    fever.py        # 发烧图点、分区、轨迹、历史时刻回放
    portfolio.py    # 组合域逻辑：鼓识别（负荷比）、错峰偏移、负荷剖面、组合视图组装
    portfolio_validation.py  # 组合/资源池载荷与加入校验（逐字段）
    storage.py      # SQLite（WAL）持久化、唯一约束、写串行化、组合两表
    api/main.py     # FastAPI 接口层 + 静态托管
  tests/            # pytest：排程/校验/汇报投影/组合/API 并发与重启
frontend/
  src/
    App.jsx, api.js, styles.css
    components/ProjectForm.jsx   # 录入 / JSON 导入 / 载入示例（资源可声明取自组合池）
    components/GanttChart.jsx    # 甘特排布，关键链与缓冲高亮
    components/FeverChart.jsx    # 发烧图轨迹，点选查看任务剩余工期
    components/ReportPanel.jsx   # 汇报提交与汇报流
    components/PortfolioForm.jsx     # 建组合：名字 + 资源池 + 可选鼓
    components/PortfolioView.jsx     # 组合视图：池维护、项目加入、冲突提示
    components/PortfolioTimeline.jsx # 组合时间轴 + 鼓负荷曲线与容量线
```

前端不做任何计划/状态计算，只调用接口展示与录入。

## 11. 测试覆盖

`backend/tests`（69 个用例）覆盖需求要求的全部要点：

- 四任务算例关键链长度 **15**、资源边 B→C；
- 无资源冲突时关键链等于关键路径；
- 工期同乘正整数（2/3/7/100）：关键链不变、长度与缓冲同比放大；
- 排程确定性；
- 全部拒收规则（逐字段）；
- 汇报乱序到达与顺序到达结果一致（含整条轨迹一致）；
- 重复汇报幂等；
- 晚到汇报插入重算；
- 历史时刻回放与前缀重放逐项相同；
- 服务重启（新建 app 指向同一 SQLite 文件）后状态/轨迹/项目列表一致；
- 并发汇报（多线程 + 打乱顺序 + 夹杂重复）状态与串行一致；
- 发烧图绿/黄/红分区与缓冲消耗；
- **组合验收算例**：池里 1 名工程师、两份四任务算例依次排入 → 偏移 0 与 9、
  第二份组合第 24 个工作日完成、全程工程师占用 ≤ 1、两份关键链都是 A/B/C/D；
  显式声明与"原样同名"两种录入方式都覆盖；
- 组合拒收：池外资源名、单任务需求超池总量、申报容量超池容量（逐字段报全）；
- 鼓：负荷比自动识别、并列取小名、管理员指定、首次识别后冻结；
- 错峰：容量 2 可并行、鼓上不留容量缓冲、间隙回填、非鼓共享资源冲突逐条列出；
- 排入并发等价于某串行顺序、鼓不超额；同输入偏移一致；
- 组合重启后成员/顺序/偏移完全一致；成员项目的原有接口行为不变。
